# Agent Note: Desktop 0.4 Runtime and Windows Integration

Status: proposed

English | [中文](2026-08-26-desktop-0.4-runtime-and-windows-integration.zh.md)

## Problem

The desktop shell owns the top-level Node runtime but only retains and kills its direct `Child`. Descendant Node processes can survive an abnormal runtime exit or application shutdown because this process is outside the managed `ctx.subprocess` service used by model tools. The title-bar balance endpoint always queries DeepSeek's official account even when the current session selects another provider, so the displayed account state can lag behind model selection. Desktop production mode suppresses the browser context menu without replacing its basic text operations. Windows composition exposes PowerShell only even when WSL 2 can provide Bash.

## Proposal

Desktop 0.4 treats these as four independently reviewable slices over one release integration pass. P1 establishes native ownership of the complete desktop runtime process tree. P2 makes account chrome a projection of the current session's provider. P3 contributes a desktop-only accessible context menu. P4 adds an opt-in WSL 2 Bash execution world on Windows. Each slice updates this note or adds a narrower Agent Note if implementation discovers a separate durable decision.

The work does not change `agent-loop`, session log formats, or the model-facing meaning of existing shell tools. A model-selection click and a context-menu action add no model-visible input. Enabling WSL changes the next request's tool catalog, so the existing system-prompt and request-header mechanisms must record that catalog without a new session event type.

## P1: own the desktop runtime tree

The Tauri shell remains the external supervisor of the Node process that runs `dsh web`; `ctx.subprocess` cannot own its own host process. Replace `DshRuntime(Mutex<Option<Child>>)` with a runtime supervisor whose state includes the root identity, platform containment handle, lifecycle state, and one idempotent `terminate_and_join(reason, budget)` operation.

On Windows, create the runtime suspended, assign it to a private Job Object configured with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, then resume it. The job must not silently fall back to direct-child ownership if creation or assignment fails: startup stops on the splash with a diagnostic because the containment guarantee is part of desktop boot. Normal exit requests graceful runtime shutdown first, waits a bounded interval, terminates the job, and waits for the root handle; shell destruction closes the job as the final synchronous backstop. The Job Object covers Node workers and descendants launched from runtime `node_modules` without process-name matching and without touching unrelated Node installations.

On POSIX, start the runtime in its own process group, send TERM to the group, wait a configurable bounded grace, then send KILL and join the root. The supervisor contains ESRCH and exit races but reports timeout and containment failures to the desktop log. `quit_app`, `RunEvent::ExitRequested`, startup timeout, readiness-channel disconnect, retry, updater relaunch, and fatal boot errors all call the same operation; no path calls `Child::kill` directly. Close-to-tray continues to keep the runtime alive.

Implementation starts with a pure lifecycle state machine and platform adapters under `apps/desktop/src-tauri/src/`; `main.rs` keeps orchestration only. Add a target-native fixture that starts a root Node process, a Node child, and a detached grandchild, prints their identities, and waits. Tests cover graceful exit, escalation, repeated termination, root exit before cleanup, startup failure after containment allocation, and application-exit cleanup. The packaged smoke must assert that no process identified by the private job/group remains; process-name-wide cleanup is forbidden.

## P2: bind balance chrome to the selected provider

The title bar needs a provider-aware account-status value, not a DeepSeek-specific polling loop. The bridge adds a typed account-summary route whose request carries the active session id and selected provider id. The Host resolves the authoritative current `ModelSelection`; it never trusts a browser-supplied endpoint or credential reference. A provider may register an effect-scoped account-summary capability returning `available`, `unsupported`, `unconfigured`, or `unavailable` plus an optional amount and currency. The DeepSeek adapter owns the current `/user/balance` implementation; providers without an account API return `unsupported`, which hides the amount and names the selected provider rather than retaining a stale prior balance.

The desktop client subscribes to the current session's `modelSelection` snapshot already owned by client runtime. Opening a session, reconnecting, or completing `session.selectModel` immediately invalidates the prior request, clears an amount from another provider, and requests the new provider's account summary. Responses carry or are checked against `{sessionId, providerId, generation}` so an older fetch cannot overwrite a newer selection. The five-minute poll and visibility refresh remain, but each poll resolves selection again. Credential and settings update events trigger a refresh through their existing forwarded events.

Do not add a title-bar-only provider-change event or infer provider state from DOM labels. Move the title-bar account controller from the injected untyped script into `bridge-client`, leaving only the stable mount point in `titlebar.js`. Focused tests cover DeepSeek success, unsupported providers, credential replacement, session switching, out-of-order replies, failed refresh after a successful value, locale changes, and disposal. The visible policy is strict: never show provider A's amount while provider B is selected.

## P3: desktop context menu

`bridge-client` replaces the production context-menu suppression with one desktop-owned body portal. Right-clicking non-editable selected text offers **Copy**. Right-clicking the active conversation composer offers **Cut**, **Copy**, and **Paste** according to selection, disabled/read-only state, and clipboard capability. Inputs outside the conversation composer receive only Copy so password, settings, and confirmation fields do not gain an accidental mutation path.

Clipboard writes use the shared clipboard primitive. Composer edits use `setRangeText` or the native textarea value setter followed by the bubbling `input` event so React and the session input machine remain authoritative. Paste reads text only, replaces the current selection, preserves undo/focus behavior where WebView support allows it, and never accepts files or HTML. The menu closes on action, Escape, outside pointer input, scroll, resize, focus loss, session navigation, or plugin disposal; keyboard navigation uses roving focus with Up, Down, Home, End, Enter, and Space. Placement clamps to the visual viewport and flips away from the lower and right edges.

Debug mode may expose an explicit **Inspect** item after the product actions; it does not restore the browser's uncontrolled menu. Tests exercise selection classification, composer-only mutation, clipboard denial, empty selection, disabled controls, IME-safe input, edge placement, keyboard navigation, locale change, and effect cleanup. A desktop browser evidence scenario and GIF are required because this changes product-user-visible GUI behavior.

## P4: opt-in WSL 2 Bash on Windows

Add a Windows-only environment card in Desktop settings. Detection runs through a bounded native command and returns a typed snapshot: `not-installed`, `no-distribution`, `wsl1-only`, `ready`, or `error`, plus eligible WSL 2 distributions and the current default. Detection uses `wsl.exe --status` and `wsl.exe --list --verbose` parsing isolated behind fixtures for localized and legacy output; activation performs an execution probe inside the selected distribution rather than trusting inventory alone. The UI offers **Enable Bash with WSL 2**, distribution selection when needed, refresh, disable, and a restart-required state if live composition cannot be made atomic.

The setting stores only `{enabled, distribution}` in the existing desktop settings namespace. It never installs WSL, changes a distribution version, changes the Windows default distribution, or downloads a distribution. Missing environments link to Microsoft's installation guidance through the native opener after explicit user action.

Implement a Windows-only WSL subprocess provider rather than teaching `bash-local` to branch on the host OS. It launches fixed `wsl.exe --distribution <name> --exec ...` argv, translates the authoritative Windows Workspace cwd through `wslpath`, scrubs credentials through the subprocess rules, and owns termination of the Windows `wsl.exe` tree. A matching Bash executor resolves commands in that execution world and registers the existing `bash` Consumer only while the setting is enabled and the probe is healthy. The ordinary `pwsh` tool remains available. Duplicate `bash` registration, a missing selected distribution, a failed path translation, or a lost distribution fails visibly and removes Bash from subsequent tool assembly.

Before implementation, P4 must prove its filesystem and sandbox semantics. The accepted design must either provide a WSL filesystem provider for the same execution world or explicitly restrict Bash cwd and file references to Windows paths translated under `/mnt`, with executor-level enforcement that matches the active permission preset. Merely wrapping commands with `wsl.exe bash -c` while leaving unrestricted Linux paths is not acceptable because it would make `ctx.fs` and `ctx.shell` disagree and bypass the Windows sandbox stance. The first release does not support WSL 1, non-default interop mounts, remote WSL hosts, automatic package installation, or persistent WSL terminals.

Unit tests cover detection parsing, probe failures, settings transitions, path translation, quoting without shell-built argv, tool registration disposal, simultaneous PowerShell and Bash catalogs, and permission denial. A Windows target-native integration test runs `bash` through a real WSL 2 distribution when available and self-skips with an explicit reason otherwise. A keyless assembled snapshot verifies that enabling Bash changes the recorded tool catalog and that disabling it removes the tool.

## Delivery sequence

1. **P0 — baselines and contracts:** reproduce the orphan with the fixture, capture the stale-balance race, inventory context-menu targets, and record WSL command output fixtures. Freeze typed interfaces and failure states before UI work. *(Status: version 0.4.0 landed; baselines for P2/P3/P4 recorded in their phases.)*

3. **P2 — account summary:** add the provider capability, move DeepSeek balance ownership, bind the desktop controller to session model selection, and remove the old unconditional endpoint.
4. **P3 — context menu:** add the portal, clipboard/edit adapters, locale strings, client tests, browser evidence, and the required GIF from the real desktop evidence server.
5. **P4a — WSL discovery UI:** land read-only detection and explicit settings state without exposing Bash.
6. **P4b — WSL execution:** land the accepted filesystem/sandbox design, provider, conditional tool composition, assembled snapshot, and Windows-native evidence.
7. **Release integration:** update desktop README/Chinese pair, changelogs, settings documentation, affected package READMEs/JSDoc, and this note; bump the single desktop version source to `0.4.0`, run version synchronization, and execute target release smokes. *(Status: version 0.4.0 landed early per the implementation request; README/zh pair updated for P1.)*

Each phase is one reviewable PR unless its implementation and evidence cannot be independently valid. Independent P2 and P3 work may proceed after the P1 interfaces settle. P4b must not merge before its permission and filesystem decision is reviewed.

## P1 implementation status (2026-08-26)

The runtime supervisor landed as `apps/desktop/src-tauri/src/runtime_supervisor.rs` (core lifecycle + `platform_windows.rs` / `platform_posix.rs` adapters). The shell state `DshRuntime(Mutex<RuntimeSupervisor>)` replaces `Mutex<Option<Child>>`; `main.rs` keeps orchestration only. Every exit path — tray quit, `RunEvent::ExitRequested`, boot timeout, readiness-channel disconnect, and show/navigate failures after readiness — funnels through `terminate_and_join(reason, budget)` with an 8-second budget. Close-to-tray keeps the runtime alive.

Windows containment spawns suspended (`CREATE_SUSPENDED | CREATE_NO_WINDOW`), assigns to a private Job Object configured with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, then resumes via `NtResumeProcess`. A failed assignment is a fatal boot error (never silent direct-child fallback). When an enclosing job refuses `CREATE_BREAKAWAY_FROM_JOB`, the spawn is retried inheriting that job and the private assignment fails loudly with a containment diagnostic — matching the note's rule that the runtime must never run uncontained. The fixture `src-tauri/tests/runtime_tree.rs` prints root/child/grandchild identities and asserts the whole tree is gone after termination; it is `#[ignore]`d on hosts where an enclosing job refuses private containment (self-skips with an explicit reason). Unit tests cover lifecycle transitions, idempotent termination, spawn from idle, and spawn-after-termination. The packaged smoke continues to assert no job/group-identified process remains (process-name cleanup remains forbidden).

## P2 implementation status (2026-08-26)

The account-summary capability landed across three surfaces. `dsh-llm` defines `AccountSummary` / `AccountSummaryState`, `LlmAdapter.accountSummary()` defaults to `unsupported`, and `LlmRuntime.accountSummary(provider)` validates and detaches the adapter result. `DeepSeekAdapter` implements it over `/user/balance` through the existing credential seam (401/403 to `unconfigured`, everything else to `unavailable`). ## P4b design decision (filesystem and sandbox semantics)

P4b implements a Windows-only WSL Bash executor and tool, without teaching `bash-local` to branch on the host OS. Because `ctx.shell` is a single-executor seam (Windows mounts pwsh-sandbox; POSIX mounts bash-sandbox), WSL Bash cannot replace `ctx.shell` without dropping PowerShell — so the WSL execution world ships as its own executor/tool pair (`bash-wsl`, `tool-bash-wsl`) plus the existing WSL discovery, registered only while the WSL setting is enabled and the probe is healthy; the ordinary `pwsh` tool stays mounted. The executor runs fixed `wsl.exe --distribution <name> --exec bash -c ...` argv through `ctx.subprocess` (no separate WSL subprocess provider needed — the local provider spawns wsl.exe), scrubs credentials through the subprocess rules, and owns termination of the Windows `wsl.exe` tree.

## Alternatives considered

**Let `ctx.subprocess` manage the desktop runtime.** Rejected because the service lives inside the Node runtime it would need to terminate and cannot provide an external crash backstop.

**Kill every `node.exe` owned by the user.** Rejected because executable names do not establish ownership and this could terminate unrelated development tools. A private Job Object or process group carries exact ownership.

**Keep the DeepSeek amount until another provider returns an amount.** Rejected because stale financial data is worse than an explicit unsupported state.

**Restore the native WebView context menu.** Rejected because it is platform-dependent, includes unwanted developer/browser actions, and cannot enforce composer-only mutations consistently.

**Expose Bash on Windows whenever `wsl.exe` exists.** Rejected because WSL 1, an absent distribution, a broken launch, or incompatible filesystem/sandbox semantics does not constitute a usable safe execution world.

**Replace PowerShell with WSL Bash.** Rejected because WSL is optional and the two tools serve different Windows workflows; enabling Bash adds a capability and does not remove PowerShell.

## Acceptance criteria

- Every supported desktop platform terminates the complete runtime-owned process tree on normal quit, boot failure, retry, and updater relaunch; the target-native fixture leaves no owned descendant, and unrelated Node processes remain alive.
- The title bar changes account state immediately with the active session's provider and never renders an amount obtained for an older session or provider.
- Production desktop right-click supports Copy for selected readable text and Cut/Copy/Paste only in the conversation composer, with keyboard and screen-reader-operable presentation.
- Windows reports WSL 2 readiness without changing the machine, enables Bash only after explicit confirmation and a successful probe, preserves PowerShell, and removes Bash when disabled or unhealthy.
- WSL Bash respects the same active workspace and permission stance as filesystem operations; no unrestricted wrapper is shipped.
- Product-visible changes have focused client tests, keyless assembled coverage where the tool catalog changes, target-native lifecycle/WSL evidence, updated bilingual documentation, and a context-menu GIF.
- `pnpm run doc-sync`, relevant focused Vitest/Cargo tests, `git diff --check`, desktop version checks, and affected target-native packaged smokes pass before release.

## Risks

Windows Job Object assignment can conflict with an enclosing job unless creation flags and breakaway behavior are tested on packaged runners. Graceful runtime shutdown may expose existing disposal latency, so budgets need diagnostics rather than silent force-kill. Provider account APIs differ and some providers will remain explicitly unsupported. Clipboard reads may require WebView permissions and user activation. WSL output localization and path mapping are unstable inputs, while WSL's Linux filesystem can escape a Windows-only workspace policy unless P4b supplies an enforcing design. These risks justify keeping the four slices independently revertible and making P1 and the P4 permission decision release gates.
