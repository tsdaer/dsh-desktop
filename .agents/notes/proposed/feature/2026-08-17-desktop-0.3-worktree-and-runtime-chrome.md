# Agent Note: Desktop 0.3 Worktree and Runtime Chrome

Status: proposed

English | [中文](2026-08-17-desktop-0.3-worktree-and-runtime-chrome.zh.md)

## Problem

The desktop client centers navigation on Workspaces and Sessions, but it does not provide a project-oriented view for inspecting files, searching source, or reading Git changes. Users must leave the application for these common orientation tasks. The title bar reports balance but not API reachability or local runtime load, its balance cannot be refreshed directly, and the splash screen uses an unrelated color block instead of the packaged application icon. The application also has no signed update path from its tag-gated GitHub Release workflow. Shared message chrome already supplies ordinary-message copy actions, but the release needs an explicit coverage audit before treating that roadmap item as complete.

## Proposal

Desktop 0.3 adds a Worktree mode beside the existing Workspace mode, gives the native chrome a compact runtime-status cluster, unifies packaged artwork, and installs signed updates published by this repository. In this proposal, “Worktree” means a project view rooted at the selected Workspace directory; it does not create, delete, or switch Git `worktree` checkouts. Ordinary-message copy remains one shared client capability: 0.3 audits its assembled renderer coverage and changes code only for a demonstrated gap.

The release remains a set of independently reviewable changes. Each product-visible implementation change updates this proposal or adds a narrower Agent Note when it introduces a durable architectural decision. The Unreleased `0.3.0` Changelog records implemented behavior and receives final shipped facts before the draft Release is published.

## Worktree mode

The existing `sidebar.workspaces` slot becomes the mounting point for a workbench owner. The owner renders a persistent, accessible Workspace/Worktree mode switch and declares one child slot for each mode. The current Workspace browser moves unchanged into the Workspace child slot. A new Worktree UI plugin occupies the Worktree child slot and owns one Explorer view with the search toolbar above the file list; Git status appears as file and directory decorations in that same tree. The selected mode is a browser-local presentation preference; changing it does not change the selected Workspace or Session.

All Worktree queries carry the selected Workspace id. The Host resolves the authoritative canonical Workspace path and rejects missing, deleted, or escaping paths. The browser never supplies an unrestricted filesystem root or command line. Requests are cancellable and bounded by entry, byte, match, and elapsed-time limits so expanding a large repository or replacing a search cannot retain obsolete work.

- Explorer loads directory children on demand, sorts directories before files, preserves expansion by Workspace, exposes loading and retry states per directory, never follows a resolved path outside the Workspace root, and lets in-root files and directories drag their relative paths into the composer.
- Search accepts partial plain text from a flexible toolbar input after a short debounce, submits immediately on Enter, streams bounded content matches while ripgrep runs, finishes with an authoritative paginated result, reports truncation explicitly, cancels the preceding query when replaced, and opens a result through the existing file-location presentation path.
- Git status discovers the repository containing the Workspace path, parses a stable machine-readable format, decorates changed files and aggregates statuses on parent directories, and is read-only in 0.3.0. A non-repository Workspace gets an explicit header state rather than a failed command card. Nested repositories resolve from the selected directory, and submodules remain parent-repository status entries without recursive queries.

The Host adapter consumes the existing filesystem and subprocess capabilities. It owns the fixed Git argv, environment, output cap, cancellation, canonical-root checks, and projection into validated RPC values. UI components consume only those projections; they do not call shell tools or the desktop bridge directly.

## Message copy

`MessageIconActions` remains the single clipboard implementation. The baseline work audits every ordinary user and assistant message renderer, including turn-tail rendering, and confirms that its complete user-visible plain text reaches the adjacent copy control. The action is visible on keyboard focus and message hover, has a persistent accessible name, reports success with the existing temporary check icon, and coexists with branch and feedback actions. Tool cards, reasoning rows, context injections, and status-only rows retain their specialized copy behavior or remain excluded when they do not represent one ordinary message. A green audit removes this item from implementation scope; a demonstrated gap receives the narrowest renderer and test change.

## API, balance, and runtime load

The title bar gains a status cluster immediately before the balance control. API state has four explicit values: checking, connected, unavailable, and unconfigured. The bridge derives the state from the same credential-safe request path used by balance, returns no credential material, distinguishes an absent credential from transport or provider failure, and retains the last successful balance while marking the current connection failure. Clicking the balance control starts one deduplicated refresh, exposes busy state to assistive technology, and cannot create overlapping polls.

The title bar also displays one load emoji with a localized accessible label. This indicator describes local application workload, not physical energy consumption. The native host samples the desktop process and its managed runtime process tree at a fixed low frequency, projects a small normalized tier, and exposes no process inventory. Threshold hysteresis and a minimum dwell time prevent rapid emoji changes. Unknown or unsupported measurements render a neutral state; telemetry failure never affects boot or agent execution.

The initial tiers are calm, active, busy, and saturated. Their exact CPU and memory thresholds are desktop-shell constants, and tests pin tier transitions, hysteresis, unsupported hosts, and teardown. The UI maps tiers to stable emoji and text without attempting to estimate watts, cost, or environmental impact.

## Icon and splash

A single black, transparent-background source asset becomes the owner of the desktop icon family. The build regenerates or verifies the PNG and ICO sizes consumed by Tauri, the installer, tray, and window. The splash screen renders the same asset in an image element instead of the gradient color block, with a light neutral backing shape that retains contrast in the dark splash theme. Asset verification rejects missing sizes and a splash reference that diverges from the packaged icon source.

## Signed automatic updates

The desktop release workflow produces Tauri v2 updater artifacts and a static `latest.json` beside the NSIS installer. The application embeds only the updater public key; the signing private key exists only as a protected GitHub Actions secret and never enters the repository, logs, uploaded generic artifacts, or installed application. The tag, package, Cargo, Tauri, Changelog, updater manifest, and Release version must agree before publication.

Update checks start after boot and never delay the splash flow, runtime readiness, or agent work. The UI reports no update, update available, download progress, signature or manifest rejection, network failure, and install readiness as explicit states. Installation requires user confirmation, uses the Windows passive installer mode, warns that the application will restart, and preserves the currently installed version when download or verification fails. Draft Releases are build products, not update endpoints; the signed manifest becomes discoverable only when the accepted Release is published.

## Alternatives considered

**Put all five changes in the injected desktop bridge.** This would make the native build faster to prototype, but it would bypass the client slot architecture, duplicate filesystem and subprocess policy, and make browser composition tests unable to exercise the Worktree UI. The bridge remains limited to native chrome and credential-safe desktop integration.

**Expose an unrestricted shell or filesystem endpoint to the browser.** A generic endpoint would reduce the number of Host methods, but it would let remote page input choose roots and commands. Fixed operations with canonical Workspace resolution keep authority narrow and make bounds testable.

**Treat Worktree mode as Git checkout management.** Creating and switching Git worktrees is destructive project mutation and requires branch, dirty-state, collision, and cleanup policy. Version 0.3 provides a read-only project worktree view; checkout management needs a separate proposal.

**Estimate physical energy consumption.** CPU utilization cannot reliably determine device power across hardware and operating systems. The emoji therefore reports application workload and labels itself accordingly.

**Create a second clipboard implementation for the new button.** The shared message chrome already handles clipboard fallback, pending writes, success timing, and teardown. Extending its renderer coverage avoids divergent behavior.

**Download and execute the latest NSIS asset without the Tauri updater.** GitHub Release ordering alone does not authenticate an installer or bind it to an accepted version manifest. Tauri updater artifacts and signature verification keep private signing material in CI and reject substituted or malformed downloads before installation.

## Acceptance criteria

- The desktop package, Rust crate, Tauri configuration, lockfile, title-bar badge, installer metadata, and draft Release agree on version `0.3.0`.
- The sidebar switch is keyboard accessible and retains Workspace/Session selection while changing modes; Explorer, Search, inline Git decorations, and Worktree-to-composer path drops remain confined to the selected Workspace and survive cancellation, reconnect, empty, error, and large-result states.
- Every ordinary user and assistant message exposes one adjacent copy action that copies the complete visible plain text and gives accessible success feedback.
- API status distinguishes checking, connected, unavailable, and unconfigured; manual balance refresh is deduplicated, preserves the last good amount on failure, and never exposes credentials.
- The load emoji changes only through the documented tiers and hysteresis, has an accessible textual state, and degrades neutrally when sampling is unavailable.
- Splash, window, tray, installer, and packaged icon assets derive from the same black source artwork and remain legible on supported backgrounds.
- The application checks for updates only after boot, accepts only a correctly signed manifest and artifact, requires user confirmation before passive installation, reports recoverable failures without interrupting agent work, and upgrades a packaged `0.2.1` installation to `0.3.0`.
- Focused unit tests, Host integration tests, assembled keyless browser scenarios, Windows packaged smokes, and product-visible GIF evidence cover the affected behavior. Documentation, lint, build, hygiene, and relevant size checks pass before publishing the draft Release.

## Risks

Large directory enumeration and repository status can consume resources precisely when the application is already busy; strict bounds, cancellation, lazy loading, and sampling intervals are release requirements rather than later optimization. Git status semantics vary for renames, submodules, ignored files, nested repositories, and non-UTF-8 paths, so 0.3.0 stays read-only and must display unsupported entries without guessing. A title bar with balance, API state, workload, version, and window controls can become crowded at narrow widths; responsive priority and accessible labels must preserve window dragging and controls. Black artwork can disappear on dark surfaces, so the canonical asset requires a backing treatment wherever the surrounding UI does not provide contrast. The updater adds key custody, artifact authenticity, downgrade, interrupted-install, and draft-versus-published Release risks; release automation must fail closed when signing input, versions, signatures, or manifest assets are missing or inconsistent.
