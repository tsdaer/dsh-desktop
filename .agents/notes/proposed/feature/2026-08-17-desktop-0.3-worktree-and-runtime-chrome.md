# Agent Note: Desktop 0.3 Worktree and Runtime Chrome

Status: proposed

English | [中文](2026-08-17-desktop-0.3-worktree-and-runtime-chrome.zh.md)

## Problem

The desktop client centers navigation on Workspaces and Sessions, but it does not provide a project-oriented view for inspecting files, searching source, or reading Git changes. Users must leave the application for these common orientation tasks. The title bar reports balance but not API reachability or local runtime load, its balance cannot be refreshed directly, and the splash screen uses an unrelated color block instead of the packaged application icon. Ordinary message copy support exists in shared message chrome, but its placement and coverage do not yet guarantee an adjacent copy action on every ordinary user and assistant message.

## Proposal

Desktop 0.3 adds a Worktree mode beside the existing Workspace mode, completes the ordinary-message copy affordance, and gives the native chrome a compact runtime-status cluster. In this proposal, “Worktree” means a project view rooted at the selected Workspace directory; it does not create, delete, or switch Git `worktree` checkouts.

The release remains a set of independently reviewable changes. Each product-visible implementation change updates this proposal or adds a narrower Agent Note when it introduces a durable architectural decision. The `0.3.0` Changelog section remains empty while development is incomplete and receives only shipped behavior before the draft Release is published.

## Worktree mode

The existing `sidebar.workspaces` slot becomes the mounting point for a workbench owner. The owner renders a persistent, accessible Workspace/Worktree mode switch and declares one child slot for each mode. The current Workspace browser moves unchanged into the Workspace child slot. A new Worktree UI plugin occupies the Worktree child slot and owns an activity switcher with Explorer, Search, and Source Control views. The selected mode and activity are browser-local presentation preferences; changing either does not change the selected Workspace or Session.

All Worktree queries carry the selected Workspace id. The Host resolves the authoritative canonical Workspace path and rejects missing, deleted, or escaping paths. The browser never supplies an unrestricted filesystem root or command line. Requests are cancellable and bounded by entry, byte, match, and elapsed-time limits so expanding a large repository or replacing a search cannot retain obsolete work.

- Explorer loads directory children on demand, sorts directories before files, preserves expansion by Workspace, exposes loading and retry states per directory, and never follows a resolved path outside the Workspace root.
- Search accepts plain text and an optional include pattern, streams or pages bounded matches, reports truncation explicitly, cancels the preceding query when replaced, and opens a result through the existing file-location presentation path.
- Source Control discovers the repository containing the Workspace path, parses a stable machine-readable Git status format, groups staged, unstaged, untracked, conflicted, and renamed paths, and is read-only in 0.3.0. A non-repository Workspace gets an explicit empty state rather than a failed command card.

The Host adapter consumes the existing filesystem and subprocess capabilities. It owns the fixed Git argv, environment, output cap, cancellation, canonical-root checks, and projection into validated RPC values. UI components consume only those projections; they do not call shell tools or the desktop bridge directly.

## Message copy

`MessageIconActions` remains the single clipboard implementation. The work audits every ordinary user and assistant message renderer, routes its complete user-visible plain text into that component, and places the copy control adjacent to the message chrome. The action is visible on keyboard focus and message hover, has a persistent accessible name, reports success with the existing temporary check icon, and coexists with branch and feedback actions. Tool cards, reasoning rows, context injections, and status-only rows retain their specialized copy behavior or remain excluded when they do not represent one ordinary message.

## API, balance, and runtime load

The title bar gains a status cluster immediately before the balance control. API state has four explicit values: checking, connected, unavailable, and unconfigured. The bridge derives the state from the same credential-safe request path used by balance, returns no credential material, distinguishes an absent credential from transport or provider failure, and retains the last successful balance while marking the current connection failure. Clicking the balance control starts one deduplicated refresh, exposes busy state to assistive technology, and cannot create overlapping polls.

The title bar also displays one load emoji with a localized accessible label. This indicator describes local application workload, not physical energy consumption. The native host samples the desktop process and its managed runtime process tree at a fixed low frequency, projects a small normalized tier, and exposes no process inventory. Threshold hysteresis and a minimum dwell time prevent rapid emoji changes. Unknown or unsupported measurements render a neutral state; telemetry failure never affects boot or agent execution.

The initial tiers are calm, active, busy, and saturated. Their exact CPU and memory thresholds are configuration values owned by the desktop shell, and tests pin tier transitions, hysteresis, unsupported hosts, and teardown. The UI maps tiers to stable emoji and text without attempting to estimate watts, cost, or environmental impact.

## Icon and splash

A single black, transparent-background source asset becomes the owner of the desktop icon family. The build regenerates or verifies the PNG and ICO sizes consumed by Tauri, the installer, tray, and window. The splash screen renders the same asset in an image element instead of the gradient color block, with a light neutral backing shape that retains contrast in the dark splash theme. Asset verification rejects missing sizes and a splash reference that diverges from the packaged icon source.

## Delivery plan

1. **Release foundation:** bump all desktop version sources to `0.3.0`, keep the Changelog section marked unreleased, define the workbench slots and bounded Host response types, and add assembled test composition for the new plugins.
2. **Low-risk interaction polish:** complete ordinary-message copy coverage and replace the icon family plus splash rendering. Record keyboard, screen-reader-name, hover, packaged icon, and splash evidence.
3. **Runtime status cluster:** add the shared API/balance refresh state machine, native load sampling, title-bar rendering, timeout and teardown behavior, and deterministic tests for every state transition.
4. **Worktree read paths:** deliver Explorer first, then Search, then read-only Source Control on the same canonical-root and cancellation infrastructure. Each view ships with its own focused Host, client, and assembled-browser tests.
5. **Release hardening:** run Windows packaged-install and upgrade smokes, verify single-instance and tray behavior remain intact, capture the required GUI GIFs from the real assembled application, update the bilingual README and Changelog with shipped behavior, and push the `v0.3.0` release tag only after every acceptance criterion passes so the tag-gated workflow creates the draft from the accepted commit.

## Alternatives considered

**Put all five changes in the injected desktop bridge.** This would make the native build faster to prototype, but it would bypass the client slot architecture, duplicate filesystem and subprocess policy, and make browser composition tests unable to exercise the Worktree UI. The bridge remains limited to native chrome and credential-safe desktop integration.

**Expose an unrestricted shell or filesystem endpoint to the browser.** A generic endpoint would reduce the number of Host methods, but it would let remote page input choose roots and commands. Fixed operations with canonical Workspace resolution keep authority narrow and make bounds testable.

**Treat Worktree mode as Git checkout management.** Creating and switching Git worktrees is destructive project mutation and requires branch, dirty-state, collision, and cleanup policy. Version 0.3 provides a read-only project worktree view; checkout management needs a separate proposal.

**Estimate physical energy consumption.** CPU utilization cannot reliably determine device power across hardware and operating systems. The emoji therefore reports application workload and labels itself accordingly.

**Create a second clipboard implementation for the new button.** The shared message chrome already handles clipboard fallback, pending writes, success timing, and teardown. Extending its renderer coverage avoids divergent behavior.

## Acceptance criteria

- The desktop package, Rust crate, Tauri configuration, lockfile, title-bar badge, installer metadata, and draft Release agree on version `0.3.0`.
- The sidebar switch is keyboard accessible and retains Workspace/Session selection while changing modes; Explorer, Search, and Source Control remain confined to the selected Workspace and survive cancellation, reconnect, empty, error, and large-result states.
- Every ordinary user and assistant message exposes one adjacent copy action that copies the complete visible plain text and gives accessible success feedback.
- API status distinguishes checking, connected, unavailable, and unconfigured; manual balance refresh is deduplicated, preserves the last good amount on failure, and never exposes credentials.
- The load emoji changes only through the documented tiers and hysteresis, has an accessible textual state, and degrades neutrally when sampling is unavailable.
- Splash, window, tray, installer, and packaged icon assets derive from the same black source artwork and remain legible on supported backgrounds.
- Focused unit tests, Host integration tests, assembled keyless browser scenarios, Windows packaged smokes, and product-visible GIF evidence cover the affected behavior. Documentation, lint, build, hygiene, and relevant size checks pass before publishing the draft Release.

## Risks

Large directory enumeration and repository status can consume resources precisely when the application is already busy; strict bounds, cancellation, lazy loading, and sampling intervals are release requirements rather than later optimization. Git status semantics vary for renames, submodules, ignored files, nested repositories, and non-UTF-8 paths, so 0.3.0 stays read-only and must display unsupported entries without guessing. A title bar with balance, API state, workload, version, and window controls can become crowded at narrow widths; responsive priority and accessible labels must preserve window dragging and controls. Black artwork can disappear on dark surfaces, so the canonical asset requires a backing treatment wherever the surrounding UI does not provide contrast.
