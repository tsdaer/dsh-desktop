# Agent Note: 桌面端签名更新器

Status: implemented

[English](2026-08-19-desktop-signed-updater.md) | 中文

## 问题

桌面发布工作流只产出 Windows 安装程序，应用也没有经过认证的路径来发现或安装后续版本。

## 决策

Tauri updater 插件负责清单解析、构件签名校验、下载和安装。应用只内置生成的公钥，并把更新器指向本仓库已发布的 `latest.json`;Windows 安装模式设为 `passive`。

主页面启动后，浏览器桥接在标题栏挂载一个紧凑的更新控制。它在启动后检查一次，对进行中的检查去重，并显示检查中、无更新、发现更新、下载中、可安装、网络失败、清单失败、签名失败和安装失败状态。下载与安装都需要用户确认。下载或安装失败时，当前应用继续运行，已安装版本不会被替换。

标签门控工作流通过 `TAURI_SIGNING_PRIVATE_KEY` 接收签名私钥，只把它传给打包步骤，并使用 Tauri `--ci` 跳过交互式密码提示；它把已签名安装程序和分离签名作为工作流构件上传，并根据同一对安装程序与签名生成 `latest.json`。有密码的私钥可以额外使用 `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`;无密码私钥不需要该 secret。清单使用 `windows-x86_64-nsis` 目标，直接嵌入签名正文，并且只在匹配的 Release 上与安装程序一起上传。缺少签名输入或签名构件时，工作流失败。

本仓库生成的私钥保存在工作树之外;提交到 `tauri.conf.json` 的只有公钥。GitHub Actions 必须配置匹配的私钥后，才能构建签名发布包。

## 测试

桥接客户端构建已通过，聚焦的更新状态与失败分类测试覆盖用户可见状态，Rust 依赖解析已包含 `tauri-plugin-updater`。清单生成器会拒绝无签名或不完整的构件目录。使用仓库私钥的本地签名 Windows 打包和清单生成已通过。受保护 CI 执行、全新安装冒烟、从 `0.2.1` 升级和已发布 Release 发现仍属于发布加固工作。

## 备选方案

**直接从 GitHub 下载最新 NSIS 安装程序。** 不采用，因为 Release 构件 URL 不能认证构件，也不能把它绑定到已接受的版本清单;Tauri 更新器会在安装前校验两者。

**让共享客户端到处暴露更新器原始插件 API。** 不采用，因为桌面桥接拥有原生集成，并把可见状态机限制在桌面标题栏。

**下载完成后立即安装。** 不采用，因为 Windows 安装会退出应用;标题栏需要第二次确认，并明确提示应用会重启。

## 后果

发布流程现在依赖一个受保护的签名 secret，并且必须发布已验收的 Release，`latest` endpoint 才能被客户端发现。Draft 构件仍可作为发布产物测试，但不是更新 endpoint。标题栏新增一个随应用语言切换标签的更新控制;控制需要足够宽度显示状态文本，并保持可重试的失败状态可见。
